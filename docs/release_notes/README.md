# Release Notes（发布说明）

本目录存放每个版本的 GitHub Release 发布说明。发布工作流
[`.github/workflows/release.yml`](../../.github/workflows/release.yml)
在发布时会自动读取这里的文件，作为 Release 的正文内容。

## 文件命名

以版本号命名，支持以下两种形式（按优先级依次查找）：

1. `v<版本号>.md` —— **推荐**，与 Git 标签保持一致，如 `v0.7.5.md`
2. `<版本号>.md` —— 不带 `v` 前缀也可以，如 `0.7.5.md`

版本号需与发布时推送的标签（以及 `lazy_mysql/.version` 中的版本）一致。

## 工作流的两种运行方式

### 1. 正式发布：推送标签（自动）

发布流程：更新版本号 → 编写本目录下的发布说明 → 提交并推送 `v*` 标签。

```bash
git tag v0.7.5
git push origin v0.7.5
```

推送标签后工作流自动执行：构建 → 测试 → 上传 PyPI → 创建 GitHub Release，
Release 正文即对应的 `.md` 文件内容。

### 2. 手动运行：Actions 页面运行

在仓库 **Actions** 页面选择工作流后点击 **Run workflow**，有两个输入项：

- **version**：版本号，填 `0.7.5` 或 `v0.7.5` 均可（仅预览时可留空）。
- **publish**：发布勾选框，**默认不勾选**。
  - 不勾选（默认）：干跑模式，只执行构建、测试并在日志中预览发布说明，
    **不会上传 PyPI，也不会创建 Release**，适合发布前检查效果。
  - 勾选：正式发布，执行与推送标签完全相同的发布流程（上传 PyPI 并创建 Release）。
    此时**必须填写版本号**，否则工作流会直接报错终止；请同时确保所选分支的代码
    和 `lazy_mysql/.version` 已更新到目标版本。若该标签尚不存在，创建 Release 时
    会在当前分支的最新提交上自动建立标签。

## 兜底机制

如果对应版本的 `.md` 文件不存在，工作流不会失败，而是自动用
**上一个标签到当前版本之间的 Git 提交记录**生成发布说明，包含每次提交的
短哈希、说明、作者和日期，并在开头标注为自动生成。首个标签则使用全部历史提交。

## 发布说明模板

新建版本文件时可参考以下结构（Markdown 格式，内容自由组织）：

```markdown
## v0.7.5

### 🚀 新功能
- 新增 xxx 方法

### 🐛 问题修复
- 修复 xxx 场景下的 xxx 问题

### ⚙️ 其他变更
- 依赖升级、文档更新等
```
