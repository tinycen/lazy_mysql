# Release 工作流支持手动运行：干跑预览 + publish 发布开关

- 日期：2026-09-30
- 类型：CI 功能增强
- 涉及提交：`88269f7`（支持手动运行和预览）、`46a9506`（修复条件判断逻辑）

## 问题描述 / 需求背景

重构后的 Release 工作流最初只保留了标签触发：

```yaml
on:
  push:
    tags:
      - 'v*'
```

由此产生两个使用诉求：

1. **无法手动运行**：GitHub 只有在工作流声明 `workflow_dispatch` 时，Actions 页面才会显示 "Run workflow" 按钮。用户希望在打标签之前先验证发布说明的渲染效果。
2. **手动运行需要可控的发布开关**：手动运行检出的代码来自分支而非 tag，若默认执行发布，会把分支代码当正式版上传 PyPI。用户最初提议用输入框 `0=不发布 / 1=发布`，最终采用更不易出错的布尔勾选框。

## 原因分析

- 没有 `workflow_dispatch` 触发器是按钮不出现的直接原因（GitHub 平台规则）。
- 手动运行与标签推送的本质差异在于 **触发 ref 不同**：
  - 推 tag：`github.ref_name` 是版本标签，创建 Release 时 action 能自动关联；
  - 手动运行：`github.ref_name` 是分支名（如 `main`），直接发布会出现「标签名错误」「Release 挂到分支语义上」等问题。

## 解决方案

### 1. 新增手动触发器与两个输入项

[release.yml 第 11-21 行](../../../../.github/workflows/release.yml#L11-L21)：

```yaml
workflow_dispatch:
  inputs:
    version:
      description: '要预览/发布的版本号，填 0.7.5 或 v0.7.5 均可；仅预览时可留空'
      required: false
      type: string
    publish:
      description: '勾选 = 正式发布（上传 PyPI 并创建 GitHub Release）；不勾 = 仅预览，不发布'
      required: false
      type: boolean
      default: false
```

- `version`：同时兼容 `0.7.5` 与 `v0.7.5`。归一化逻辑为先去 `v` 再补 `v`：`CURRENT_TAG="v${INPUT_VERSION#v}"`，保证后续文件查找与 git 范围计算始终使用统一格式。
- `publish`：原生 boolean 勾选框，默认不勾选（干跑），比手输 0/1 更直观。

### 2. 发布步骤加条件，干跑自动跳过

[release.yml 第 186-204 行](../../../../.github/workflows/release.yml#L186-L204)，PyPI 上传与 Release 创建均加相同条件：

```yaml
if: github.event_name == 'push' || inputs.publish == true
```

即「推 tag」或「手动且勾选 publish」才发布；默认手动运行只构建、测试、打印发布说明。

### 3. 安全校验：勾选发布必须填版本号

[release.yml 第 78-82 行](../../../../.github/workflows/release.yml#L78-L82)：

```bash
if [ "${{ github.event_name }}" = "workflow_dispatch" ] \
   && [ "$PUBLISH" = "true" ] && [ -z "$INPUT_VERSION" ]; then
  echo "::error::勾选了正式发布，但未填写版本号。请填写版本号（如 0.7.5）后重新运行。"
  exit 1
fi
```

不填版本号时 `CURRENT_TAG` 会退化为分支名（如 `main`），可能造成错误发布，因此在任何发布动作之前以 `::error::` + `exit 1` 终止。

### 4. Release 显式指定标签

新增 step 输出 `release_tag`（规范化后的 `v0.7.5`），创建 Release 时通过 `tag_name` 显式指定：

```yaml
tag_name: ${{ steps.prepare_release_notes.outputs.release_tag }}
```

若该标签尚不存在，GitHub 会在所选分支最新提交上自动建立标签；同时要求发布前更新 `lazy_mysql/.version`。

### 5. 预览态的展示与提示细节

- 干跑生成的兜底标题追加「（手动预览，不会实际发布）」；勾选 publish 时不加该标识，避免正式 Release 文案出现误导。
- 勾选 publish 时日志输出 `::warning::`，明确提醒本次将真实发布。
- 预览时若目标版本的 ref 尚不存在（打标签前的典型场景），提交范围终点自动回退为 `HEAD`（`git rev-parse --verify "${CURRENT_TAG}^{commit}"` 判断）。

## 验证结果

- 推送到默认分支后，Actions 页面出现 Run workflow 按钮，含版本号输入框与 publish 勾选框。
- 手动运行（不勾选）时构建、测试正常，发布步骤被跳过，日志打印完整发布说明。
- 首次带勾选的运行暴露了一个 bash 语法错误（见关联文档），修复后流程恢复；该错误与本次功能逻辑无关。

## 注意事项

- **PyPI 同版本号不可覆盖上传**：对已发布版本（如 0.7.4）勾选发布会在 twine 阶段失败。建议先干跑确认，正式发布使用新版本号并先更新 `.version`。
- `workflow_dispatch` 的按钮只对**默认分支上的工作流文件**生效，改动需先合入默认分支。
