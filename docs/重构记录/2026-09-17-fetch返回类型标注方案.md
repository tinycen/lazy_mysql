# fetch 返回类型标注方案（FetchMode / OutputFormat / show_count）

> 日期：2026-09-17
> 范围：`lazy_mysql/tools/result_formatter.py`、`lazy_mysql/executor.py`（`fetch_format` / `select` / `query`）、`lazy_mysql/crud/select.py`

## 一、问题现状

`fetch_mode`、`output_format`、`show_count` 三个参数共同决定查询返回类型，但当前所有相关函数均无返回类型注解，导致：

1. IDE（Pyright/Pylance）无法静态推断返回类型，调用方拿到 `Unknown`，链式调用 `.to_csv()`、`len()` 等全部失去补全与检查；
2. 类型约束分散在 docstring 中，与实际行为无强绑定，容易漂移。

涉及函数（共 5 处，存在同一返回矩阵的重复描述）：

| 位置 | 层级 |
|---|---|
| `tools/result_formatter.py :: fetch_format()` | 底层实现 |
| `executor.py :: SQLExecutor.fetch_format()` | 底层包装 |
| `crud/select.py :: select()` | CRUD 实现 |
| `executor.py :: SQLExecutor.select()` | 用户入口 |
| `executor.py :: SQLExecutor.query()` | 用户入口 |

## 二、返回类型矩阵（事实源）

普通游标（dict_cursor=False）：

| fetch_mode | output_format | show_count | 返回类型 |
|---|---|---|---|
| `"all"` | `""` | False | `list[tuple]` |
| `"all"` | `"list_1"` | False | `list[Any]` |
| `"all"` | `"df"` | False | `pandas.DataFrame` |
| `"all"` | `"df_dict"` | False | `list[dict]` |
| `"all"` | 任意 | True | `tuple[数据, int]` |
| `"oneTuple"` | `""` | False | `tuple | None` |
| `"oneTuple"` | `"dict"` / `"df_dict"` | False | `dict \| None` |
| `"one"` | （忽略） | False | `Any | None` |

dict_cursor=True 时：`"all"+""` → `list[dict]`；`"oneTuple"+""` → `dict | None`；其余受限格式抛 ValueError。

## 三、方案对比

### 方案 A：仅加联合返回别名（低成本，收益有限）

定义一次类型别名，全部函数统一标注：

```python
QueryResult = Union[
    list[tuple], list[Any], pd.DataFrame, list[dict],
    tuple, dict, Any, None, tuple["QueryResult", int],
]
```

- 优点：一处定义、零重复、改动最小；
- 缺点：IDE 只知道"可能是这些类型之一"，无法按配置收窄，调用方仍需 `assert isinstance(...)` 或类型 ignore。

### 方案 B：FetchConfig 字面量子类 + @overload（推荐）

利用 Pydantic 支持字段级 `Literal` 收窄的特性，为每种"返回形态"定义 FetchConfig 子类，再对用户入口函数做 `@overload`：

```python
# models/fetch_config.py 新增
class FetchAllTuples(FetchConfig):
    fetch_mode: Literal["all"] = "all"
    output_format: Literal[""] = ""

class FetchAllList1(FetchConfig):
    fetch_mode: Literal["all"] = "all"
    output_format: Literal["list_1"] = "list_1"

class FetchAllDf(FetchConfig):
    fetch_mode: Literal["all"] = "all"
    output_format: Literal["df"] = "df"

class FetchAllDfDict(FetchConfig):
    fetch_mode: Literal["all"] = "all"
    output_format: Literal["df_dict"] = "df_dict"

class FetchOneTuple(FetchConfig):
    fetch_mode: Literal["oneTuple"] = "oneTuple"
    output_format: Literal[""] = ""

class FetchOneDict(FetchConfig):
    fetch_mode: Literal["oneTuple"] = "oneTuple"
    output_format: Literal["dict"] = "dict"

class FetchOne(FetchConfig):
    fetch_mode: Literal["one"] = "one"
```

```python
# executor.py 用户入口（仅 select / query 需要，底层不需要）
@overload
def select(self, ..., fetch_config: FetchAllDf, ...) -> pd.DataFrame: ...
@overload
def select(self, ..., fetch_config: FetchAllDfDict, ...) -> list[dict]: ...
@overload
def select(self, ..., fetch_config: FetchOneDict, ...) -> dict | None: ...
# ... 其余子类各一个 overload
@overload
def select(self, ..., fetch_config: FetchConfig | dict[str, Any] | None, ...) -> QueryResult: ...  # 兜底
```

- 优点：
  - IDE 可精确收窄：`executor.select(..., fetch_config=FetchAllDf())` 直接推断为 `DataFrame`；
  - 运行时零开销（Pydantic 子类即普通模型，校验逻辑不变）；
  - 底层 3 处（`result_formatter.fetch_format`、`executor.fetch_format`、`crud.select`）只需标注 `QueryResult` 联合别名，**@overload 只写在 2 个用户入口**，避免 5 处重复；
- 缺点：
  - `@overload` 在 `select` 与 `query` 各写一遍（约 8 个签名 × 2），是"必要重复"而非"散乱重复"；
  - 传 dict 字面量的旧用法无法收窄，走兜底签名返回联合类型。

### 方案 C：泛型 TypeVar（不推荐）

用 `FetchConfig[Literal["all"], Literal["df"]]` 协变泛型建模。理论优雅，但 Pydantic 泛型模型 + 协变 TypeVar 在 Pyright 下推断不稳定，且对使用者的心智负担更高，收益不优于方案 B。

## 四、show_count 的处理建议

`show_count=True` 仅在 `fetch_mode="all"` 时生效，返回 `tuple[数据, int]`。两个可选处理：

1. **简单方案（推荐）**：不为 show_count 单独建子类，在兜底签名的 `QueryResult` 中包含 `tuple[QueryResult, int]`，docstring 说明。代价是 show_count 用户无精确收窄；
2. **完整方案**：为 `FetchAll*` 系列再派生 `FetchAllDfCount` 等 4 个 `show_count: Literal[True] = True` 子类，overload 数量翻倍。仅在确实有大量 `show_count=True` 调用方时才值得。

## 五、实施步骤（建议分两阶段）

### 阶段 1：联合别名铺底（低风险，先行合入）

1. 在 `models/fetch_config.py` 定义 `QueryResult` 别名并导出；
2. 为 5 处函数统一加 `-> QueryResult` 返回注解（含 `crud/select.py :: exists()` 已有 `-> bool`，不动）；
3. 同步修正 docstring 与矩阵不一致处。

### 阶段 2：overload 精确收窄

1. 新增 `FetchAllTuples / FetchAllList1 / FetchAllDf / FetchAllDfDict / FetchOneTuple / FetchOneDict / FetchOne` 子类，从 `lazy_mysql.models` 导出；
2. `executor.select()` 与 `executor.query()` 添加 `@overload` 签名组；
3. 底层 `fetch_format`（tools 与 executor 两处）和 `crud/select.py :: select()` 保持 `QueryResult` 联合注解，不写 overload；
4. `dict` 传参路径维持兜底签名，行为不变，零破坏性。

## 六、顺带发现的待确认问题

`result_formatter.py` 第 64-70 行：`fetch_mode="oneTuple"` + `output_format="dict"` 分支执行 `dict(zip(data_label, myresult))`。当 executor 以 `dict_cursor=True` 初始化时，`myresult` 本身已是 `dict`，`zip(data_label, myresult)` 实际 zip 的是其键序列，结果取决于字段顺序巧合而非语义。docstring 声称 dict_cursor 下支持该组合，实现与声明不符，建议在本次重构中一并核实修正。

## 七、结论

推荐 **方案 B（分两阶段实施）**：
- 阶段 1 用联合别名消除 5 处 `Unknown`，成本最低、零风险；
- 阶段 2 用 FetchConfig 子类 + `@overload` 在两个用户入口实现精确收窄；
- `@overload` 刻意只落在用户入口（`select` / `query`），底层统一用 `QueryResult`，将"多处重复"收敛为"一处定义 + 两处入口声明"。

### 实施中发现与解决的两个静态检查问题

1. **overload 参数默认值歧义**：子类 overload 若给 `fetch_config` 设默认值 `= ...`，则"省略参数"的调用会同时匹配多个签名（返回类型互不兼容），触发 `reportOverlappingOverload`。
   解决：overload 存根中将 `fetch_config` 声明为 `*` 后的**关键字必传**参数（`*, fetch_config: FetchAllDf`），与实现签名（位置或关键字均可）兼容；按位置传 `fetch_config` 的旧调用自动落入兜底签名，行为不变。
2. **pydantic 子类 Literal 收窄误报**：pyright 对可变属性逆变规则报 `reportIncompatibleVariableOverride`，属 pydantic 场景已知误报（运行时由 Pydantic 校验兜底），已逐行 `# pyright: ignore[reportIncompatibleVariableOverride]` 忽略并注明原因。

### 推断效果（pyright 1.1.410 实测）

| 调用 | 推断类型 |
|---|---|
| `executor.select("t", ["a"])` | `list[tuple]` |
| `executor.select(..., fetch_config=FetchAllDf())` | `DataFrame` |
| `executor.select(..., fetch_config=FetchAllDfDict())` | `list[dict]` |
| `executor.select(..., fetch_config=FetchOneDict(data_label=[...]))` | `dict | None` |
| `executor.select(..., fetch_config=FetchConfig())` 或 dict 传参 | `QueryResult`（联合） |
| `executor.query("SELECT 1")` | `list[dict]`（None 默认 df_dict） |
| `executor.select("t", 123, fetch_config=FetchAllDf())` | 报错：fields 类型不符（中间参数检查保留） |

### 第六节问题修复

`result_formatter.py` 的 `oneTuple` 分支：`dict_cursor=True` 时 `fetchone()` 已返回 `dict`，原实现 `dict(zip(data_label, myresult))` 会 zip 到字典的**键序列**，返回 `{data_label[i]: 列名}` 的错配结果。现增加 `isinstance(myresult, dict)` 判断，字典游标结果直接返回，与 docstring 声明行为一致。

## 九、补充重构：消除 mutable-attribute override 报错（2026-09-17）

### 问题

Trae（VSCode 系）内置的 **Pyrefly** 检查器报 `bad-override-mutable-attribute`：
`FetchAllDf.fetch_mode`（`Literal['all']`）与 `FetchConfig.fetch_mode`（`FetchMode`）类型不一致——
"可读写属性不能在子类中收窄"。Pyrefly 不识别 `# pyright: ignore` 注释，且规则比 pyright 更严格。

### 根治方案：拆分字段声明层级，子类不再覆写任何字段

将公共字段上提为 `_FetchConfigBase`（仅含 `data_label` / `show_count` / `to_dict`），
`fetch_mode` / `output_format` 只在各叶子类中声明：

```
_FetchConfigBase (data_label, show_count, to_dict)
├── FetchConfig          (fetch_mode: FetchMode,    output_format: OutputFormat)
├── FetchAllTuples       (fetch_mode: Literal["all"],    output_format: Literal[""])
├── FetchAllDf           (fetch_mode: Literal["all"],    output_format: Literal["df"])
└── ... 其余 5 个形态类
```

- 全类型树中**不存在任何字段覆写**，`bad-override-mutable-attribute` /
  `reportIncompatibleVariableOverride` 从根源不再触发，**删除了全部 14 行 pyright ignore 注释**；
- `FetchAllDf` 不再是 `FetchConfig` 的子类（平级），故新增 `FetchConfigLike` 联合别名
  （8 种形态之并集）用于实现签名与底层函数参数标注（`executor.select/query/fetch_and_response`、
  `crud/select.py select`）；
- `to_dict()` 改为基于 `model_dump()` 实现（行为等价，返回全部字段）。

### 连带修复：table/fix_column.py

`fetch_format` 加返回注解后暴露的真实类型问题：`for index, old_value in result` 处
`result` 为 `QueryResult` 联合类型（含 `None` 等），Pyrefly 报 not-iterable。
改为类型化入口 `executor.query(sql, fetch_config=FetchAllTuples())`（精确返回 `list[tuple]`），
并移除两处已无必要的 `# pyright: ignore`。

### 最终验证

- `pyrefly check lazy_mysql`：**0 errors**
- `pyright lazy_mysql`：**0 errors, 0 warnings**
- 运行时导入正常
